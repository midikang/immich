What Immich Does (And What Happens When You Upload a Photo)

Imagine you have thousands of photos on your phone — family memories, vacation snapshots, random screenshots. They're all stuck on your device, taking up space, and you're worried about losing them if something happens to your phone.

Immich is your personal photo manager. It's like having your own private Google Photos or iCloud Photos, but running on your own computer or server. You control where your photos live, who can see them, and how they're organized.

Here's what makes Immich special:

📱
Auto Backup
Open the app, and photos automatically sync from your phone to your server. No button clicking needed.
🔍
Smart Search
Find photos by searching "beach" or "dog" — even if you never tagged them. The AI reads what's in the picture.
👤
Face Recognition
The app automatically groups photos by the people in them. Search for a person, see all their photos.
🗺️
Map View
See where you took each photo on a map. Relive your travels visually.
🔐
Full Privacy
Everything runs on hardware you control. No company analyzing your photos in the cloud.
🌐
Multi-Platform
Mobile app for iOS and Android, plus a web interface you can access from any browser.

Let's break down each step to understand what's really happening:

Step 1: The Mobile App Sends Your Photo

When you tap upload, the mobile app doesn't just throw the photo file at the server. It carefully packages the photo with important information:

  • The actual image file (the pixels that make up your dog photo)
  • Metadata like when the photo was taken, where it was taken (GPS coordinates), and what device captured it
  • A unique ID for your device (so Immich knows this photo came from *your* phone)
  • Authentication credentials (proves you have permission to upload)
💡 Why This Matters for You

When you're building with AI tools, understanding this step helps you debug upload failures. If a photo doesn't appear, you can ask: "Did the mobile app successfully package the data? Did authentication work? Did the network request make it to the server?" Each piece of this flow is a potential failure point you need to check.

The app sends this package to the server using an API call. Think of an API as a waiter in a restaurant — you tell the waiter what you want (upload this photo), and the waiter takes your request to the kitchen (the server).

Step 2: The API Server Receives and Validates

Your photo arrives at Immich's backend server, specifically at an endpoint designed to handle uploads. The server acts like a bouncer at a club — it checks your credentials before letting the photo in:

The Code
@Post()
@Authenticated({ permission: Permission.AssetCreate })
uploadAsset(@Auth() auth: AuthDto, @Body() dto: AssetUploadDto) {
  return this.service.uploadFile(auth, dto);
}
What It Means
This is a POST endpoint — it receives data from the mobile app.
The @Authenticated decorator checks if you're logged in and have permission to create assets (upload photos).
If you pass the check, it calls the service layer to actually handle the upload.
The service layer is where the real work happens — storing the file, extracting metadata, etc.

If authentication fails (maybe your login token expired), the server rejects the upload immediately. You'd see an error in the app: "Session expired, please log in again."

If authentication succeeds, the server moves on to the next step: saving your photo.

Step 3: Saving the Photo to Storage

The server needs to store your photo file somewhere permanent. It doesn't keep photos in memory (that would be lost if the server restarts) — it writes them to disk.

Immich uses a storage template system. Think of it like a filing cabinet with a specific folder structure. Your photo might be saved to a path like:

/upload/library/your-user-id/2026/03/your-dog-photo.jpg

This structure makes it easy to find photos later. Each user has their own folder, organized by year and month. The server also generates a thumbnail (a smaller version of the photo for fast loading in the gallery view).

💡 Why This Matters for You

When you're using AI to build similar apps, the storage strategy is a key architectural decision. Do you store files locally, or use cloud storage like S3? How do you organize files so they're easy to retrieve? Understanding Immich's approach gives you a pattern to copy or improve on.

Step 4: Extracting Metadata

Photos contain hidden data beyond just pixels. This is called EXIF data, and it includes things like:

  • Camera model (iPhone 15, Canon EOS, etc.)
  • GPS coordinates (where the photo was taken)
  • Date and time the photo was captured
  • Camera settings (shutter speed, ISO, aperture)

Immich uses a tool called ExifTool to read this data. It's like a photo detective that can pull out all these hidden details. The server extracts the EXIF data and stores it in the database so you can later search photos by location, date, or camera.

Step 5: The Machine Learning Worker Takes Over

Here's where things get interesting. Your photo isn't done processing yet. It gets added to a job queue for the machine learning worker to analyze.

Think of a job queue like a to-do list. The API server says "I've saved this photo, but it still needs ML analysis" and adds it to the list. The ML worker picks up jobs from this list and processes them one by one.

The ML worker does three main things:

🔍
Object Detection
Uses a CLIP model to identify what's in the photo (dog, beach, car, etc.). This powers search.
👤
Face Recognition
Detects faces and creates embeddings (mathematical representations) to group photos by person.
🏷️
Smart Tagging
Automatically tags the photo with keywords based on what the AI sees.

All of this analysis data gets stored in the database. Now when you search "dog," Immich can find your photo because the ML worker tagged it with "dog."

Step 6: Saved in the Database

The final step is saving everything to the database. Think of the database like a massive spreadsheet that keeps track of all your photos and their metadata.

For your dog photo, the database stores:

  • The file path where the photo is stored on disk
  • When it was uploaded and when it was taken
  • GPS coordinates (for map view)
  • Tags generated by the ML worker ("dog," "outdoor," "grass," etc.)
  • Face embeddings (if people are detected)
  • Which user owns this photo

Now your photo is fully processed. You can search for it, view it on the map, or find it by browsing your timeline. All in a matter of seconds from when you tapped upload.

The Cast of Characters: Who Does What in Immich

Immich isn't one big program — it's a team of specialized components working together. Each component has a specific job, like actors in a play. Understanding who does what helps you know where to look when building new features or debugging problems.

Let's meet the main characters:

📱
Mobile App (Flutter)
The iOS and Android apps users interact with. Built with Flutter (a cross-platform framework). Handles photo upload, browsing, and syncing.
🌐
Web App (Svelte)
The browser interface at demo.immich.app. Built with Svelte (a modern web framework). Mirrors mobile app features but runs in any browser.
🔧
API Server (NestJS)
The backend brain. Built with NestJS (a Node.js framework). Handles authentication, file uploads, and coordinates all other services.
🧠
ML Worker (Python)
The machine learning engine. Built with Python. Runs face recognition, object detection, and smart tagging using AI models.
🗄️
PostgreSQL Database
The library catalog. Stores all metadata, user accounts, tags, and search indexes. Not where photos are stored — that's in file storage.
⚡
Redis Cache
The speedster. Stores temporary data like job queues and session tokens for ultra-fast access. Basically short-term memory.

How They Work Together

Imagine you're browsing photos on the web app. Behind the scenes, here's who's doing what:

The API Server: The Traffic Controller

The API server is the most important component. It's like an air traffic controller — coordinating everything and making sure requests go to the right place.

Here's what the API server is responsible for:

The Code (app.module.ts)
@Module({
  controllers: [
    AssetController,
    AuthController,
    AlbumController,
    PersonController,
    SearchController,
    // ...many more
  ],
  providers: [
    AssetService,
    AuthService,
    StorageService,
    // ...corresponding services
  ]
})
What It Means
Controllers are like receptionists — they receive requests from mobile/web and decide what to do.
Each controller handles a specific domain: assets (photos), auth (login), albums, people, search, etc.
Services contain the actual business logic — "how do I save a photo?" or "how do I authenticate this user?"
This separation (controllers handle requests, services do the work) is a common pattern in backend development.
💡 Why This Matters for You

When you're asking an AI to "add a feature to Immich," you need to know which component to modify. Want to add a new search filter? You'd update the SearchController and SearchService. Want to change how photos are stored? That's the StorageService. Knowing the cast helps you give AI precise instructions like "modify the AssetService to support video transcoding."

The ML Worker: The Brain

The ML worker runs separately from the API server. Why? Because machine learning is computationally expensive. If the API server tried to run ML models while also handling uploads and authentication, everything would slow down.

Instead, the ML worker is a separate process that picks up jobs from the queue and processes them one at a time. It's like having a dedicated photo analyst who works in the background while the rest of the team handles day-to-day operations.

The ML worker uses specialized AI models:

  • CLIP — a model that understands what objects are in photos (can you spot a dog vs a cat?)
  • InsightFace — detects and recognizes faces, creating mathematical "fingerprints" for each person
  • PaddleOCR — reads text from photos (like signs, documents, or screenshots)

These models run using GPU acceleration if available (much faster than CPU), but can fall back to CPU if needed.

Why Separate Web and Mobile Apps?

You might wonder: why have both a web app and a mobile app? Why not just one?

The answer is about reaching users where they are:

📱
Mobile App
Best for: Automatic backup, browsing on the go, and taking new photos. Needs to run in the background to sync photos even when you're not actively using it.
🌐
Web App
Best for: Admin tasks, bulk photo management, and accessing from any device with a browser. No installation needed.

They both talk to the same API server, so your photos and settings stay in sync. Add a photo on mobile, it appears on web instantly (and vice versa).

How Data Flows: From Your Phone to the Database

Now that you know the cast of characters, let's understand how they talk to each other. In Immich, data is constantly flowing between components — from your phone to the server, from the server to the database, from the ML worker back to the web app.

Understanding these data flows is crucial when you're debugging issues or building new features. Let's trace a few common scenarios.

Authentication: The Bouncer System

Before you can upload photos or view anything, you need to prove you're allowed to access the system. This is called authentication.

Here's the authentication flow when you log in to the mobile app:

1. You Enter Credentials
Mobile app → API server with email/password
→
2. Server Checks Database
Does this user exist? Is the password correct?
→
3. Server Generates Token
Creates a JWT — like a temporary hall pass
→
4. App Stores Token
Saved locally, sent with every future request

A JWT (JSON Web Token) is like a movie ticket — it proves you paid to get in, and the theater (server) can verify it's legitimate. Every time you make a request (upload a photo, view an album), your app sends this token to prove you're authorized.

💡 Why This Matters for You

When users report "I keep getting logged out" or "my uploads fail randomly," the issue is often token expiration. Understanding the auth flow helps you debug: Is the token expiring too quickly? Is the app not refreshing it? Is the server rejecting valid tokens? Each step is a potential failure point.

Search: Finding Needles in Digital Haystacks

When you type "beach" into the search bar, how does Immich find photos of beaches — even if you never tagged them? Let's trace the search flow:

Search Controller Code
@Get('search')
@Authenticated()
search(@Query() query: SearchDto) {
  return this.searchService
    .searchAssets(query);
}
What It Means
When you search, the web/mobile app sends a GET request to the search endpoint.
The query contains your search term ("beach") plus optional filters (date range, person, etc.).
The SearchService handles the actual searching logic.
Results come back as a list of matching photos with their metadata.

Behind the scenes, the SearchService queries the database for photos that match your term. But how does the database know which photos have beaches? That's thanks to the ML worker from earlier — it analyzed every photo and stored tags like "beach," "ocean," "sand" in the database.

The search uses something called vector search. Instead of just matching exact words, it understands concepts. Searching "beach" might also find photos tagged "ocean" or "coast" because they're conceptually similar.

Sharing: Letting Others See Your Photos

When you share an album with a friend, what actually happens? Let's trace the sharing flow:

Shared links work by creating a temporary public URL that doesn't require login. The link contains a unique token that grants access to specific photos. When someone clicks the link, the server checks if that token is valid and, if so, serves the photos.

💡 Why This Matters for You

Understanding sharing flows is critical for security. If you're building a similar feature, you need to think: How do you grant access without requiring login? How do you revoke access later? What prevents someone from guessing valid share links? Immich's approach (unique tokens, optional passwords, expiration dates) gives you a pattern to follow.

The Machine Learning Magic: How Photos Become Searchable

The coolest part of Immich is its AI-powered features: face recognition, object detection, and smart search. But how does a computer "know" there's a dog in your photo? Let's demystify the machine learning worker.

The Three ML Models

Immich uses three specialized AI models, each with a different superpower:

🔍
CLIP (Object Detection)
Understands what objects are in a photo. Trained on millions of images to recognize dogs, cars, beaches, mountains, etc. Powers the search feature.
👤
InsightFace (Face Recognition)
Detects faces and creates unique "fingerprints" for each person. Groups photos by who's in them. Can recognize the same person across different photos.
📝
PaddleOCR (Text Reading)
Reads text from images — street signs, documents, screenshots, memes. Makes text content searchable.

How CLIP Understands Images

CLIP is the most magical part. It doesn't just match keywords — it actually "understands" what's in a photo conceptually. Here's how it works:

Imagine showing a photo to a very smart friend and asking "What's in this?" They might say "a golden retriever playing in a park on a sunny day." CLIP does something similar, but mathematically.

🧮 The Math Behind the Magic

CLIP converts your photo into a list of numbers called an embedding — think of it like a photo's fingerprint. Photos of dogs have similar fingerprints to other dog photos. When you search "dog," CLIP compares your search term's fingerprint to all photo fingerprints and finds the closest matches. This is why it works even if you never manually tagged anything.

The embedding is stored in the database alongside each photo. When you search, the system compares your search query's embedding to all stored embeddings and returns the closest matches. It's like asking "which photos have fingerprints similar to the fingerprint of the word 'beach'?"

Face Recognition: The Two-Step Dance

Face recognition is more complex than object detection because it needs to answer two questions:

  1. Are there faces in this photo? (Face Detection)
  2. Whose face is this? (Face Recognition)
Step 1: Face Detection
Find all faces in the photo (bounding boxes)
→
Step 2: Face Embeddings
Create a unique "fingerprint" for each face
→
Step 3: Clustering
Group similar faces together (same person)
→
Step 4: User Labels
You label one cluster "Mom" — all photos update

The cool part is step 3: clustering. The system automatically groups faces that look similar, even before you label anyone. It's saying "I found 47 photos with this face, 23 with this other face, etc." You just need to label one photo in each cluster, and the whole cluster gets labeled.

The Performance Trade-off

Running AI models is computationally expensive. Processing one photo might take 2-5 seconds on a CPU, but only 0.2 seconds on a GPU. This is why Immich supports GPU acceleration.

Here's the trade-off you face when self-hosting Immich:

🐢
CPU Only
Slower: 2-5 seconds per photo. Fine for small libraries (hundreds of photos). No special hardware needed.
🚀
GPU Accelerated
Much Faster: 0.2-0.5 seconds per photo. Essential for large libraries (thousands of photos). Requires NVIDIA GPU or compatible hardware.
💡 Why This Matters for You

When building AI-powered apps with AI coding tools, hardware is a key decision. Do you run ML on the server (like Immich) or in the browser (using TensorFlow.js)? Server-side gives you access to GPUs but requires backend infrastructure. Client-side (browser) is easier to deploy but limited by device performance. Understanding Immich's choice helps you make informed decisions for your own projects.

Storage and Database: Where Everything Lives

Immich stores two types of data: the actual photo files (pixels) and metadata about those photos (who, what, when, where). Understanding the difference is key to debugging storage issues and making smart architectural decisions.

Files vs. Metadata: A Critical Distinction

🖼️
File Storage (Disk)
The actual photo and video files. Stored as files on disk (or S3-compatible object storage). Large but simple — just files in folders.
🗄️
Metadata (PostgreSQL)
Information *about* the files: file paths, upload dates, GPS coords, tags, embeddings, user IDs. Small but complex — supports fast queries and relationships.

Think of it like a library: the books are file storage (bulky, stored on shelves), and the card catalog is the database (compact, lets you find books instantly).

🤔 Why Not Store Photos in the Database?

Databases are optimized for structured data and fast queries, not large binary files. Storing a 5MB photo in PostgreSQL would slow down queries and waste database resources. Files go on disk; metadata goes in the database. This separation is a fundamental pattern in web development.

The Database Schema: What Gets Stored

The PostgreSQL database stores dozens of tables, each tracking a different aspect of your photo library. Here are the most important ones:

Assets Table (Simplified)
table assets {
  id: uuid
  userId: uuid
  originalPath: string
  createdAt: timestamp
  latitude: number
  longitude: number
  deviceId: string
  isFavorite: boolean
}
What It Means
Each photo is an "asset" with a unique ID.
userId links the photo to its owner.
originalPath tells the server where the file is on disk.
GPS coordinates enable map view.
Favorite status, device info, and upload time are all here.

Other important tables include:

  • smart_search — stores CLIP embeddings for each photo (the "fingerprints" for search)
  • person — tracks detected people and their names
  • face — stores face embeddings and links them to photos and people
  • album — groups photos into collections
  • shared_link — tracks public share links and their permissions

These tables are connected through foreign keys — like arrows pointing from one table to another. For example, the faces table points to both the assets table (which photo is this?) and the person table (whose face is this?).

Storage Templates: Organizing Files on Disk

Immich doesn't just dump photos randomly on disk. It uses a configurable template to organize files systematically. The default template is:

/upload/library/{userId}/{year}/{month}/{filename}

So your dog photo from March 2026 might live at:

/upload/library/abc123-def456.../2026/03/IMG_5678.jpg

This structure has several benefits:

  • Easy to find files manually if needed (browse to the year/month folder)
  • Users are isolated (each has their own folder)
  • Backup is simpler (back up user folders separately)
  • Performance stays good (folders don't get too large)
💡 Why This Matters for You

When building file storage features with AI tools, you need to think about organization strategy. A flat folder (all files in one directory) works for 100 files but breaks down at 100,000. Immich's template system is a pattern you can reuse — organize by user, then by time, to keep folders manageable.

Redis: The Speed Demon

Immich also uses Redis, an in-memory data store that's incredibly fast. Redis handles:

📋
Job Queues
The to-do list of pending ML jobs. Redis is perfect for this because it's fast and supports queue operations natively.
🎫
Session Tokens
Your login tokens are cached in Redis for ultra-fast authentication checks. Checking Redis is faster than querying PostgreSQL.
⚡
Temporary Data
Short-lived data that doesn't need to be permanent, like rate limiting counters or active upload sessions.

Think of Redis like your brain's short-term memory — it's lightning fast but limited in capacity. PostgreSQL is long-term memory — slower but permanent and unlimited.

Key Design Decisions and Why They Matter

Immich's architecture isn't random — every choice solves a specific problem. Let's look at the key decisions and what you can learn from them:

🧩
Separate ML Worker
Why: ML is slow and CPU-intensive. Separating it keeps the API fast. Lesson: Isolate expensive operations so they don't block critical paths.
📦
Files on Disk, Metadata in DB
Why: Databases excel at queries, not binary files. Lesson: Use the right tool for the job — don't store large files in a database.
🔄
Job Queues (Redis)
Why: Asynchronous processing keeps uploads fast. Lesson: Queue slow tasks instead of making users wait.
🎯
Shared API for Web + Mobile
Why: One API means one source of truth and less code to maintain. Lesson: Build platform-agnostic APIs that any client can use.
🔐
JWT Authentication
Why: Stateless tokens scale better than sessions. Lesson: Stateless auth lets you add servers without sharing session state.
🚀
Optional GPU Acceleration
Why: Makes ML feasible for large libraries. Lesson: Design for hardware optionality — work on CPU but fly on GPU.
